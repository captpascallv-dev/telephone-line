# Architecture

The Harness Telephone Line is transport infrastructure. It carries one request to an external Windows command and returns one durable result to the exact original Codex CLI Lead session. It does not judge project content, correctness, acceptance, review outcome, stage, or scope.

v0.1 is Codex-first. Codex CLI is the only currently built-in Lead maintained by the original project team. Other frozen Harness routes are execution or review sides, not substitute Lead entries. Codex plans, dispatches, accepts, advances, exits after dispatch, and resumes on the exact durable callback. Community Lead extensions remain welcome after they pass the unified transport contract, advertised native-session recovery, Lead sleep and callback, no whole-task timeout, privacy and compatibility tests, and code review. The frozen v0.1 denominator is exactly eight routes, and no ninth is planned.

Supported DeepSea routes use one shape: Codex Lead -> Telephone Line -> DSH Harness -> model provider inside DSH -> exact original Codex Lead callback. DSH owns the agent loop, tools, permissions, workflow, and session. A provider or auth library is model transport only. The Run Card is never sent to Codex CLI, Cursor Agent, Grok CLI, ACP, or another autonomous Harness.

## Lifecycle

1. A caller supplies a dispatch request, a frozen Lead binding, a frozen adapter command, and an explicit runtime state root.
2. For a wired run under the installed copy, `Start-TelephoneWiredRun.ps1` validates the request, atomically publishes it to the supervisor inbox, triggers the registered per-user Task Scheduler task, and returns with `lead_should_exit_now=true`. It does not own process lifetime.
3. The Task Scheduler-created hidden limited-user supervisor claims the request and starts a long-lived run host. That run host creates the named Windows Job with `KILL_ON_JOB_CLOSE`, records itself as durable owner, launches the initial wired Lead into the Job, and waits on exact Job process membership until the command host, relay, collector/dispatcher, executor, and callback/resumed Lead descendants drain or an exact stop occurs. The initial Lead may exit immediately after dispatch; a dead Lead with live owned descendants is not completion or failure. Cancel, emergency stop, Doctor, dashboard, and uninstall keep control through named Job plus run-id plus owner/start ticks plus membership, and reject PID reuse, a missing Job, and foreign processes. The supervisor carries the base install root and the pinned `versions/<id>` runtime as two canonical, reparse-safe identities: the run host and inherited Telephone processes load the pinned version bytes for that Job, and after that exact named Job reaches zero members the run host activates `pending.json` against the base install root, never against the version directory. Concurrent drainers serialize on one install-activation mutex so the last idle transition switches dest files, manifest, and `current.json` exactly once.
4. `Start-TelephoneLineJob.ps1` still validates the request, publishes a new job identity, and starts the command host and relay. When that starter is invoked directly, it returns immediately with `lead_should_exit_now=true` and never waits for the external command. A supervised wired Lead may start multiple batch-declared jobs; each relay is a producer into the accepted shared mailbox, never a competing sender.
5. The command host publishes owner identity before invoking the frozen command and later publishes a create-new receipt.
6. The relay waits until that receipt exists and validates against the dispatch. Nested-target hops still complete on the job relay. The relay then atomically enqueues one immutable mailbox item for the exact Lead and attaches one per-Lead collector/dispatcher. Under a supervisor run that collector remains inside the named Job (or is otherwise durably bound to that exact run owner/Job). It preserves FIFO, closes a declared batch only at exact `N/N`, and wakes the exact Lead session once with one batch manifest (an undeclared dispatch is implicit `1/1`). Committed collection `k/N` is published into per-Lead observational truth before or with `collection.json` visibility; status and dashboard only read that truth and correlate it to the exact supervisor run plus Lead/batch identity without wildcard adoption. A busy Lead receives no competing marker turn; collecting or queued-behind-busy is wait, not `LEAD_WAKE_AMBIGUOUS`.
7. `Resume-TelephoneLines.ps1` recovers interrupted or undelivered jobs without starting a replacement command. Supervisor resume does not resurrect cancelled or completed batches. There is no whole-wave timeout and no blind executor rerun.

One immutable line-job ID binds one validated dispatch, one frozen adapter command, one exact Lead binding, and one terminal receipt. Durable objects are published atomically and are never overwritten. The accepted shared mailbox (per-Lead items, collection, closed manifest, and collector owner) is the only mailbox truth; the supervisor does not keep a second mailbox. Supervisor inbox, claimed, outbox, run-owner, and mailbox-binding records bind protocol, exact run-id, request bytes and hash, project and stage, Lead identity, command and worktree, installed-version identity, the live run-host PID and UTC start ticks, current Job-member identities, timestamps, and terminal. Same-byte replay is idempotent. Same run-id with different bytes fails closed. Pascal control (`status`, `cancel-one`, `pause`, `emergency-stop-all`, `resume`) plus the desktop console never depend on Codex remaining alive. Exact cancel/emergency stops only the supervisor-owned Job, including collector and relay processes, latches pause, and preserves mailbox/partial evidence. Resume clears intake pause, triggers the registered supervisor to process only legitimate queued work, and never resurrects canceled or completed runs. Natural completion leaves zero collector/run owner, held Job/mutex/lock, or queue residue.

## Continuity

Transport continuity is mandatory for every route: immutable dispatch, receipt, and delivery identity; callback to the exact original Codex Lead; no blind rerun; recoverable transport state; and no absolute whole-task timeout.

Executor-native same-session resume is a per-adapter capability advertised as `exact_native_session`. A descriptor may set that boolean to `false`. `follow_up` is exact-id only when advertised. `recover` may return already durable transport state without starting or replacing external work and does not imply native-session continuation.

## Read-only dashboard

The bundled dashboard is an observational projection over user-configured descriptors and StateRoots plus the public lifecycle files already published by wired jobs and wireless App Server runs. Optional supervisor lineage, status, and mailbox Lead/batch identity may be correlated to the exact project plus Lead/run/job. Wildcard adoption of a foreign mailbox or supervisor run is refused. It can show active, paused, cancelled, failed, orphan, duplicate, and version-drift truth. Groups still hide only after the existing terminal, closure, and zero-residue rule. The observer never controls the supervisor, never mutates task or supervisor state, and is compatible with the external global-dashboard consumer. Wired and wireless transports share one ensure entry and one lifecycle-event schema. The reducer accepts the real relay order `dispatched → execution → nested_target → owner_acceptance → delivered` without accepting skipped or reverse transitions. Lifecycle identity includes `lead_run_id`. Path, reparse, and bounded-read checks cover dashboard state, config, descriptors, jobs, runs, sessions, lifecycle files, and closure receipts; a refused dashboard-state path creates no target write. The watcher is a single local process reused by PID and start identity. It cannot dispatch, retry, judge PASS, or mutate task state. See [dashboard.md](dashboard.md).

## Boundaries

- Runtime state root, workspace, launcher, executable, and adapter locations are configuration or explicit caller input.
- There is no absolute whole-task timeout. Optional bounded startup probes may exist; long valid route work may run indefinitely.
- Interrupted or ambiguous work is sealed or reported. It is never automatically rerun.
- The core does not branch on route names. Later adapters attach through the small replaceable contract without editing core.
- DeepSea adapters select a frozen provider plus a validated model and reasoning effort from route configuration before DSH receives the bounded user task. They do not ask a model to choose a route.
- Windows is the only v0.1 production target.

## Codex app-server Lead callback

New-Lead activation is one durable lifecycle: the same app-server process performs `thread/start` and the first `turn/start`, then publishes the ordinary binding after the turn is accepted. This closes the zero-turn process boundary without adding an execution route or changing the eight-route denominator.

CLI upgrades are fail-closed and data-driven. `CodexAppServerCompatibility.psd1` retains independently approved whole-schema and relevant-surface identities plus a version-scoped adapter rule. The qualification command regenerates both identities without starting a thread; an identical surface can reuse one existing rule by adding a reviewed catalog record, while any relevant surface or live response change requires a scoped adapter update and the wireless five-check smoke before promotion.

The relevant surface includes `ServerNotification.json`. The 0.149 adapter rule validates optional notification `emittedAtMs` as a nonnegative int64 before ignoring it, so `turn/completed` remains reachable; the 0.147 rule retains the strict legacy envelope.

An adjacent Lead-side adapter under `src/lead-side/codex-app-server/` uses the official stable Codex app-server stdio protocol to persist the exact thread id, resume that thread after process replacement, and deliver one Telephone Line callback as one turn. If that exact Lead still has an active owning turn — including an App-native turn this adapter does not own — the durable callback stays `queued` until the thread is eligible, then one marker-matching callback is sent or attached. A busy thread is not `LEAD_WAKE_AMBIGUOUS` and does not rerun the executor. It binds `serviceTier: "default"`, the canonical resolved executable path and bytes/hash, schema fingerprint, and profile SHA-256. `thread/start` and `thread/resume` send that exact default in the request dictionary they construct and accept JSON-null or exact `default` as default only from that evidence; blank returned strings fail. After exact 0.147 profile/schema binding, known serializer extras on those responses are passively ignored (not stable generated API fields); experimental API stays disabled and unknown extras are still rejected. Durable JSON uses same-directory flush plus Windows `File.Replace`. Each F02 persistence writer is independently crashable as a labeled fail-fast process death at temp-flush, replace, durable publication, or declaration delete; those injected crashes terminate outside worker catch and never become a second failure or recovery world. `run.json` `callback_write_phase` is callback-write authority, including `terminal_publishing` plus `terminal_target` before official terminal artifacts; `transitions.jsonl` is diagnostic only. A durable worker keeps one stdout read alive after `turn/start` so launcher return cannot close an accepted callback; a quiet interval is not a failure. Official matching `completed`, `failed`, and `interrupted` terminals are distinct from a nonterminal `recovery_required` transport-loss state recorded in `recovery.json`. Failure snapshots and recovery.json are separate atomic replacements; recovery.json is durable before run disposition becomes `recovery_required`. Exact same-turn proof retires failure, persists idempotent recovered run state, then retires recovery.json before bind/ack so those declarations cannot leak into later phases. Catch persistence cannot move `recovery_required` back to `in_progress`, recreate retired declarations, or enable CLI fallback; once `terminal_publishing` and `terminal_target` are persisted, an ordinary bound/ack exception keeps that publication authority so the next launch finishes the same official terminal from disk before owner, worker, or app-server action. Trusted inbound events bind to the exact generated shapes and the exact bound thread and turn. Durable intent/run/bound-turn/ack/owner/final records are checked as a chain, including identity-bound `launcher-result.json`, `failure.json`, `recovery.json`, and the phase table, before returning existing or contacting app-server. Recovery and failure records are accepted only when a finite writer-derived history table relates the recorded snapshot to the actual current run phase, disposition, and required thread/turn state; that table is the exact reachable writer set after real replacement boundaries, including writer-scoped fail-fast crash windows, and is not a retained-declaration forward table, broad allowlist, ordinal comparison, terminal failure-history rows, or a self-planted copy of itself. An independent disjoint writer oracle observes attributable declaration tuples at those named persistence boundaries without final-byte-change credit, kind filters, owner-local unique projection, or post-capture suppression. Planted declarations are excluded only when the exact declaration path, canonical key, and bytes already matched the starting world; a changed canonical key or a same-key byte change is submitted even when the other is unchanged. Each unique canonical tuple has a real production-call inventory owner. The two alternative real failure-record then recovery-required sequences at each origin submit the same recovery tuple twice, so passing inventories keep closed accounting (`raw_captured = submitted = unique + duplicates`) as 48 raw, 48 submitted, 44 unique, four scenario-duplicate recovery rows, and zero production-table duplicates. After independent submission the observed set is compared with the production relation. After the official terminal result is persisted, those declarations are retired crash-safely so a repeat launcher returns the same terminal from disk. Future, stale, reverse, skipped, and otherwise unreachable combinations fail closed with the durable bytes preserved. Existing results are never deleted to make validation pass. Marker recovery requires exact generated `userMessage` keys (`type`, `id`, `clientId`, `content`) and text members (`type`, `text`, `text_elements`); aliases are invalid. Binding output and state stay outside the product package for both app-server and explicit CLI transports. Public errors are categorical codes, not truncated exception text, including profile and launcher entry scripts. Status is observational, contained outside the package (state root, `runs`, and run root), and re-filters pending methods. It is not an execution route. The frozen v0.1 denominator is exactly eight routes, and no ninth is planned. The current CLI Lead callback remains an explicit fallback chosen before dispatch. See [codex-app-server-lead.md](codex-app-server-lead.md).
