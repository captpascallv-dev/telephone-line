# Direct PI

Direct PI is an execution and review side for the built-in Codex CLI Lead. It is not a Lead entry.

The adapter discovers Node and the PI coding-agent CLI from explicit arguments or PATH. A PATH-discovered `.ps1` launcher or explicit `.ps1` target is invoked with PowerShell. A `.cmd` / `.exe` shim is invoked with its native Windows host. A JavaScript program is invoked with Node. Tests use a mock CLI seam and never read live interactive session directories.

`start` creates one session-file identity under the caller-supplied state root. `follow_up` requires that exact native session id and the saved session file. `recover` returns existing durable state without starting a replacement process. When the adapter binding is missing after a wrapper failure but the native session is durably finished, explicit `recover` with the original `JobId`, `NativeSessionId`, and `ResumeSessionPath` may restore that same-session binding. Before writing a binding it must prove, from the trusted original job, that request and `receipt.terminal_result` path/bytes/SHA exist and match the current files, that job/session/path/workspace/provider/model/effort and native exit 0 are exact, and that the latest selected native branch/turn is closed. It does not treat any historical assistant stop as the latest turn, does not treat request labels as a substitute for native observation, and refuses a new user/tool, `toolUse` / `toolResult` without a later completed assistant, unknown stop reasons, open, forked, compacted, or otherwise unproven tails. The observed thinking is the configuration used by that final completed assistant, not a later change. Legitimate post-end metadata is not a new turn. It keeps the original failed receipt/result bytes, does not forge `agent_end`, does not rewrite wrapper failure as success, and does not start a model or new session. Live owners, native writers, identity or hash mismatches, missing/unknown effort, and conflicting bindings are refused. Prompt bytes are sent on stdin and are not copied into argv or request metadata. There is no absolute whole-task timeout.

Native JSON event stdout is parsed record-by-record. `MaxOutputBytes` (default 16 MiB) bounds each LF JSON event, not the whole stream. Session files keep the original larger bound. A sidecar `transport-diagnostics.json` records only byte counts, hashes, event counts, and fixed failure stage/type/line. It does not store exception text, stdout/stderr bodies, prompts, replies, or credentials. `event_count` remains the actual total event count in the existing 21-key result schema. This is not a general huge-stream scalability claim.

`Provider`, `Model`, and `ThinkingLevel` default to `xai` / `grok-4.6` / `xhigh` for compatibility. Explicit values are written into the durable request and checked against the native result. `follow_up` keeps the same native session, session file, and model binding; a different provider/model/thinking is refused. The adapter checks the invoked executable path and content identity, then checks the native final assistant `provider`/`model` against the frozen request. Missing or mismatched native identity cannot succeed; a successful result keeps the observed assistant identity rather than copying the request labels. It does not pin a PI CLI version number.
