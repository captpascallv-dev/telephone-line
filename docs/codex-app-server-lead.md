# Codex app-server Lead callback

This is a Windows-only, MPL-2.0 **Lead-side adapter**. It uses the official stable Codex app-server stdio protocol to persist the exact `thread.id`, resume that thread after the app-server process is replaced, and deliver one Telephone Line callback as one turn. It is not an execution route. Codex CLI remains the package's built-in Lead. The frozen v0.1 denominator is exactly eight routes, and no ninth is planned.

It supplements the existing caller-supplied CLI Lead callback. CLI fallback is an explicit binding choice made before dispatch. The adapter never launches CLI automatically after a wake intent or an app-server turn attempt.

## Desktop visibility and writer ownership

The durable thread can appear automatically in Codex App because the App and CLI use the same local conversation store. That does not create a second Lead or a second safe writer. While the CLI Lead owns an active turn, do not send App messages into that thread; the safest operational choice on current desktop builds is to leave it unopened until terminal, then use the App entry for inspection or archiving. If a desktop build behaves differently, preserve the one-writer invariant rather than assuming that UI visibility grants concurrent ownership.

The accepted local Windows runtime has completed three consecutive automatic callbacks to the same frozen Lead session with three distinct bound turns, FIFO order, and zero surviving owner or held lock. This is evidence for the accepted local runtime, not a claim that another user's Codex version, paths, profile, or desktop state is already configured.

## What it does

1. Binds the installed Codex executable and the generated stable app-server schema fingerprint.
2. Creates a durable new Lead by issuing stable `thread/start` and its first `turn/start` in one app-server process, or adopts an exact thread through stable `thread/resume` plus `thread/read`.
3. Emits the ordinary `telephone-line-lead-binding-v1` object whose `session_id` is that thread id; durable-create mode publishes it only after the first turn is accepted.
4. Wakes that exact thread through the generic launcher signature `-WorktreePath`, `-PromptFile`, `-ResumeSessionId`, `-RunId`.
5. Recovers exactly once across launcher, app-server, turn-start, receipt, and acknowledgment crash boundaries.
6. Projects stable `notLoaded`, `idle`, `systemError`, and `active` status plus `waitingOnApproval` / `waitingOnUserInput` when those flags are exposed.

WebSocket, the Unix daemon, dynamic tools, `experimentalApi=true`, experimental turn pagination or direct-input fields, and other OS support are refused.

## Profile and preflight

Resolve an explicit Codex executable, read `codex --version`, generate the stable app-server schema into a private temporary directory, fingerprint that finite file set, hash the resolved executable, and bind `service_tier` to the stable explicit default `default`. Native cleanup leaves no schema temp residue. Before every thread create/resume or wake, the adapter regenerates and compares the canonical resolved Codex executable path and bytes/hash, Codex version, generated schema identity, immutable profile identity, and service tier. A mismatch before `run.json` `callback_write_phase` leaves `none` fails closed with sanitized `fallback_required=cli`. Once phase is `turn_start_sending`, or a turn is bound or acknowledged, the same drift is a fail-closed `recovery_required` state for that callback: it writes `recovery.json`, never advertises CLI fallback, and never writes `launcher-final`.

Approved CLI identities live in `CodexAppServerCompatibility.psd1`. Each record binds the exact version, whole generated-schema identity, relevant 12-file surface identity (including the server-notification envelope), service tier, adapter rule, and version-specific serializer behavior. The shipped catalog independently qualifies `codex-cli 0.147.0`, `codex-cli 0.149.0`, and `codex-cli 0.149.1`; the two 0.149 patch versions have identical generated-schema identities and share one adapter rule. 0.149 permits only JSON-null `thread.projectId` and an optional nonnegative int64 notification `emittedAtMs`; 0.147 requires `projectId` absent and retains its strict notification envelope.

Before updating Codex CLI, run the isolated qualification command. It starts no thread or model turn. An exact approved record returns `approved=true`. An unknown version whose identical-surface records all agree on one adapter rule and serializer modes returns `record_only_candidate=true`; an unmatched or internally conflicting surface returns `requires_adapter_change=true`.

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/Invoke-CodexAppServerCompatibilityQualification.ps1 -CodexCommand YOUR_CANDIDATE_CODEX -OutputPath YOUR_QUALIFICATION_JSON
```

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/Invoke-CodexAppServerLeadProfile.ps1 -CodexCommand YOUR_CODEX -OutputPath YOUR_PROFILE_JSON
```

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/Invoke-CodexAppServerLeadPreflight.ps1 -CodexCommand YOUR_CODEX -WorktreePath YOUR_WORKTREE -StateRoot YOUR_STATE_ROOT -ProfilePath YOUR_PROFILE_JSON
```

Preflight is read-only with respect to threads and turns. `allow_fast` is false. There is no absolute task timeout.

After qualification and before promotion, run the five-check wireless smoke in a disposable external scratch root. It deliberately starts two minimal model turns and therefore requires the explicit `-AllowModelTurns` switch. It proves approved profile/preflight, durable create plus first turn, exact callback, restart/exact resume, and unknown-profile fail-closed behavior.

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/Invoke-WirelessTelephoneSmoke.ps1 -CodexCommand YOUR_CANDIDATE_CODEX -ScratchRoot YOUR_NEW_EXTERNAL_SCRATCH -AllowModelTurns
```

## Builder

The ID-only form creates or adopts a Lead binding. It does not start Telephone Line, an execution route, or a turn beyond the stable stdio app-server handshake needed to obtain or adopt the thread id.

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/New-CodexAppServerLeadBinding.ps1 -WorktreePath YOUR_WORKTREE -StateRoot YOUR_STATE_ROOT -BindingOutputPath YOUR_BINDING_JSON -CallbackTransport app-server -CodexCommand YOUR_CODEX
```

For a new durable Lead, add the first prompt and one deterministic run id. This formal create mode keeps `thread/start` and the first `turn/start` in the same app-server process, publishes the binding after that turn is accepted, and returns after the exact `turn.started` acknowledgment while the durable worker continues. It refuses an existing binding, run, owner, or session id and never creates a second replacement.

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/New-CodexAppServerLeadBinding.ps1 -WorktreePath YOUR_WORKTREE -StateRoot YOUR_STATE_ROOT -BindingOutputPath YOUR_BINDING_JSON -CallbackTransport app-server -CodexCommand YOUR_CODEX -ProfilePath YOUR_PROFILE_JSON -PromptFile YOUR_FIRST_LEAD_PROMPT -RunId YOUR_FIRST_RUN_ID
```

An ID-only zero-turn `thread/start` is not a durable cross-process Lead activation. Use the combined form above whenever the new thread must survive the builder process and immediately become the callback owner. Existing durable threads continue to use exact `thread/resume` and the ordinary launcher.

`-CallbackTransport cli` with `-CliLauncher` and `-ResumeSessionId` emits the ordinary Lead binding that points at the preselected CLI launcher. That is the explicit fallback. It does not start app-server. `BindingOutputPath` is canonicalized first: the parent chain, including the nearest existing ancestor when the leaf is absent, must have no reparse component, must stay outside the product package, and must not be the package or product root or a nested path under it. The same containment applies to both `app-server` and `cli` transports. Rejection happens before profile, store, app-server, or binding publication.

## Launcher

The per-Lead mailbox and one collector/dispatcher own batch fan-in. Relays only enqueue a frozen mailbox item; they do not compete as per-callback senders. A declared batch closes once at exact `N/N` and delivers one marker turn carrying one immutable manifest. A dispatch without a batch declaration is implicit `1/1`. A normal active App Server turn leaves batch callbacks queued and starts no marker turn; busy is wait, not `LEAD_WAKE_AMBIGUOUS` and not executor failure. The relay already calls this generic shape. `-ResumeSessionId` is the exact Codex thread id. Durable per-run state lives under the caller-supplied `-StateRoot`, outside the package. A launcher invocation durably enqueues the callback intent (exact thread, worktree, run id, prompt bytes/SHA-256, wake marker, profile/runtime identity, and `service_tier=default`) before any owner launch. One live callback owner per durable thread, identified by PID plus start ticks, serializes queued callbacks FIFO with at most one app-server client and one active callback turn. Repeated launcher or relay attachment for the same run is idempotent and never creates a competing temporary app-server client. A valid live exact thread owner is an attachment target, not a conflict: a later durable callback stays queued without an absolute queue or turn timeout and later receives exactly one marker turn and ack. A real competing owner claim fails only at the atomic thread-owner claim with public `THREAD_OWNER_CONFLICT`; the queued item remains recoverable, no second client overlaps, and the executor is not rerun. Observed `callback_owner_state` is derived from the durable run/failure chain; a stale status value such as `callback_active` cannot override completed, failed, interrupted, recovered, or `recovery_required`. Owner death before bind restarts only the owner and consumes the same durable item. Child, network, or stdio loss after send recovers the same marker/turn and never sends a replacement callback turn. Completed, failed, and interrupted items retire their per-run owner projection while the thread owner may remain alive for later queue items, then bounded idle quiesce leaves zero temporary owner. One exclusive per-run gate still makes concurrent launches attach to the same run. They never start two turns.

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/Invoke-CodexAppServerLeadLauncher.ps1 -WorktreePath YOUR_WORKTREE -PromptFile YOUR_PROMPT_FILE -ResumeSessionId YOUR_THREAD_ID -RunId YOUR_RUN_ID -StateRoot YOUR_STATE_ROOT -CodexCommand YOUR_CODEX -ProfilePath YOUR_PROFILE_JSON
```

The callback turn includes the wake prompt plus a non-sensitive deterministic `tl-wake:<RunId>` marker. Durable adapter records store path/bytes/SHA-256 and that marker. They do not store raw prompt text, thread history, command text, file-change contents, reasoning, tokens, credentials, or approval/user-input payloads.

`turn/start` success binds exactly one turn id and writes the generic `turn.started` wake acknowledgment. It is not `turn/completed`. In durable-create mode the same worker owns both `thread/start` and that first `turn/start`, closing the zero-turn process boundary before the binding is published. A durable worker keeps one coherent stdout read alive after launcher return so the relay can resume while the callback turn continues. After that acknowledgment, a quiet interval is not a failure and does not impose an idle or absolute turn-duration timeout. Startup/binding probes may remain bounded only where they do not terminate an already accepted turn.

Thread create, exact resume, and callback `turn/start` construct and send a params dictionary that itself contains exact `serviceTier: "default"`. Response acceptance uses that same request evidence: a JSON-null returned tier or the exact string `default` means default only then. An omitted, inherited, blank, or nondefault request, a blank/empty returned string, or an explicit `priority`, Fast, Flex, `ultrafast`, or other nondefault returned value, fails before binding publication. After exact approved executable/version/generated-schema/profile binding succeeds, known serializer extras (`runtimeWorkspaceRoots`, `activePermissionProfile`, `multiAgentMode` on start; those plus `initialTurnsPage`, `turnsBackwardsCursor`, and `itemsBackwardsCursor` on resume; nested `Thread` `extra`, `historyMode`, and `canAcceptDirectInput`) are passively ignored after validation. Version-scoped rules additionally require `projectId` absent on 0.147 and JSON-null on 0.149. These extras are not stable generated API fields. Admission requires exact catalog evidence, validates those payloads then ignores them, never consumes or persists them, keeps `experimentalApi=false`, and still rejects unknown extras including root `backwardsCursor`, `nextCursor`, and `selectedCapabilityRoots`. `turn/start` results use official `TurnStartResponse` `{ turn }` only. Inbound `thread/status/changed`, `serverRequest/resolved`, and `turn/completed` notifications must match their generated shapes before any mutation. The 0.149 rule accepts the generated optional `emittedAtMs` envelope field only as a nonnegative int64 and otherwise ignores it; 0.147 keeps the strict two-key notification envelope. `serverRequest/resolved` accepts only `threadId` and `requestId`. Marker recovery requires each candidate `userMessage` to be the exact generated dictionary with only and all `type`, `id`, `clientId`, and `content`. `type` must be `userMessage`, `id` a nonempty string, `clientId` the generated string-or-null, and `content` an actual JSON array of generated `UserInput` members. A marker-authoritative text member must contain only and all `type`, `text`, and `text_elements`, with `type=text`, a string `text`, and an actual array of generated `TextElement` values. Unknown, missing, malformed, or convenience-alias members (`user`, `input_text`, `inputText`) invalidate the whole candidate message and never authorize a marker.

Durable JSON records are published by writing a complete temp file in the same directory, flushing it, then using Windows `File.Replace` / `File.Move` so abrupt loss keeps either the complete prior record or the complete new record. Forced profile replacement uses that same helper and does not delete first. `run.json` `callback_write_phase` is the durable callback-write authority (`none`, `turn_start_sending`, `turn_bound`, `acknowledged`, `terminal_publishing`, `terminal`). Terminal publication first persists `terminal_publishing` plus exact `terminal_target` in `run.json` before `launcher-final`, terminal bound, terminal run, and the official `launcher-result.json` projection. Phase changes use the same flushed helper. `transitions.jsonl` is diagnostic only and does not decide fallback, recovery, or exactly-once. Official `launcher-final` is reserved for exact `completed` / `failed` / `interrupted`. Recovery metadata uses `recovery.json`. Existing `launcher-result.json` is identity-bound to the current `run_id`, canonical `run_root`, and an allowed state for the current phase; a legal prior result may be superseded only by an allowed forward transition and is never deleted to make validation pass.

Matching stable `completed`, `failed`, and `interrupted` values are three distinct proven terminals. Each updates the exact bound turn and run, clears pending state, writes `launcher-final`, and makes a repeat launcher return that existing terminal without starting a worker or another turn. A crash during that publication re-enters one of the exact `terminal_publishing` intermediate states and finishes it forward from disk before owner, worker, or app-server action. App-server process exit, worker death, or stdio loss after ack and before matching terminal proof is not an official interrupted turn. That case persists nonterminal `recovery_required`, keeps the selected thread/turn, and reconciles the same turn on restart. It never infers success, failure, or interruption from transport loss and never starts a second marker turn.

Run and `launcher-final` terminal states are written only after the matching stable `turn/completed` notification or an equally exact stable `thread/read` that proves one of those three terminals. Launcher exit does not close or kill that worker. An official terminal without the complete intent/run/bound/ack/final chain fails closed. Validly shaped but impossible intent/run/bound/ack/final/result/recovery/failure combinations, including unauthorized crash windows, fail closed before owner liveness, worker creation, or app-server contact.

Inbound `thread/status/changed`, the four allowed pending methods, `serverRequest/resolved`, and `turn/completed` mutate this run only when the installed stable identity fields match the exact bound thread and turn. Missing thread ids are not synthesized. A resolution missing `threadId`, a malformed same-thread event, extra identity, or extra `turnId` on `serverRequest/resolved` cannot clear pending or change status. A missing, malformed, aliased, or unknown terminal disposition is never defaulted to `completed`. Raw params and payloads are not persisted.

If the process dies after an ambiguous write, recovery resumes the exact thread and uses stable `thread/read` with `includeTurns=true` in memory to locate that marker in the exact `userMessage` text input the adapter created. Assistant, tool, reasoning, error, and output strings are not a match. Exactly one matching nonempty turn id is recovered and acknowledged. No match after `callback_write_phase` is no longer `none` persists `recovery_required` and does not start another turn. Multiple, empty, echoed, conflicting, or unexplained new turns fail closed. Every first or repeat invocation validates the durable intent, run, bound-turn, ack, owner, child, result, failure, and official final chain, including the phase/dependency table that covers result, recovery, and failure identity and semantics, before residue cleanup, owner liveness, worker creation, or app-server contact. Recovery and failure declarations are related to the current run through one finite writer-derived history table: the exact reachable writer set after real replacement boundaries, including writer-scoped fail-fast crash windows of failure snapshot, recovery declaration, recovery-required run and bound, catch-run, bind/ack, recovery-commit (`recovered` run with `recovery.json` still present), declaration retirement, and failure-only leftover evidence before bind. It is not a retained-declaration forward table and does not authorize terminal failure-history rows after declarations are retired. An independent disjoint writer oracle captures attributable tuples at those named persistence boundaries without final-byte-change credit, kind filters, owner-local unique projection, production-table filtering, or post-capture suppression. Planted declarations are excluded only when the exact declaration path, canonical key, and bytes already matched the starting world; a changed canonical key or a same-key byte change is submitted even when the other is unchanged. Each unique canonical tuple has a real production-call inventory owner. The two alternative real failure-record then recovery-required sequences at each origin submit the same recovery tuple twice, so passing inventories keep closed accounting (`raw_captured = submitted = unique + duplicates`) as 48 raw, 48 submitted, 44 unique, four scenario-duplicate recovery rows, and zero production-table duplicates. After independent submission the observed set is compared with the production relation. Each of those writers is independently crashable as a real process death at temp-flush, replace, durable publication, or delete; re-entry is through the public launcher after whole-chain validation. `Write-CodexAppServerFailureRecord` is a separate atomic replacement from `Write-CodexAppServerRecoveryRequired`; recovery.json is durable before run disposition becomes `recovery_required`. After exact same-turn proof (existing bound/ack identity or one verified marker turn matching the immutable wake text and baseline), recovery-commit retires `failure.json`, persists idempotent `recovered` run state without inventing a selected turn, then retires `recovery.json` before bind/ack. A crash at each of those replacements remains valid and resumable. Production re-enters bind/ack only when recovery authority is absent, so declarations cannot leak into turn-bound, acknowledged/in-progress, `terminal_publishing`, or official terminal. Catch handling cannot move `recovery_required` backward to `in_progress`, recreate retired declarations, start another turn/callback, or enable CLI fallback. After `terminal_publishing` plus `terminal_target` are persisted, an ordinary bound/ack exception keeps that publication disposition so the next launch validates the chain and completes the same official terminal, thread, and turn from disk before owner, worker, provider, or turn activity. After the official terminal result is persisted, any leftover recovery and failure declarations are retired crash-safely so a repeat launcher returns that same terminal without provider contact. Future, stale, reverse, skipped, terminal-to-preterminal, and otherwise unreachable combinations fail closed and do not delete `launcher-result.json`. A malformed, cross-run, or conflicting `launcher-result.json` is never deleted. A malformed owner is invalid authority and is not replaced. Orphan, extra-field, cross-thread, cross-turn, wrong canonical root, stale state, phase-conflict, and conflicting combinations fail closed. Recovery may complete only a known legitimate crash window: intent-only, intent+run, bound before ack, ack after exact bound before selected-run update, empty-turn `turn_start_sending` marker recovery, recovered-turn `turn_bound` and acknowledged in-progress intermediates, `terminal_publishing` intermediates, fully acknowledged nonterminal recovery, and official terminal.

Pending records are sanitized method/id for the stable methods `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, and `item/tool/requestUserInput` only. `serverRequest/resolved` and turn terminal/status transitions clear pending and flags. Redirected stderr is drained continuously; only bounded categorical counts are persisted. Public failures use an allowlisted categorical code and a fixed public message; caught exception text is not truncated into stdout, stderr, durable state, or status. Profile and launcher entry scripts apply that same public-error boundary.

## Status

Observational only. It never starts or resumes a process, never sends `serverRequest/resolved`, never clears a pending request, and never drives routing. Projected `callback_owner_state` distinguishes `queued`, `callback_active`, `recovered`, `completed`, `failed`, and `recovery_required`. Collecting `k/N` and queued-behind-busy mailbox truth is wait, not product or executor failure; committed collection is readable from `collection.json` before or with `truth.json`, and the dashboard remains read-only and cannot trigger recovery. `RunId` is validated before path join. The normalized run root must be an exact child of the intermediate `runs` directory under the normalized state root, outside the product package, with no reparse component on the state root, `runs` directory, run root, status-sources file, or referenced roots even when the run leaf does not yet exist. Status sources use a strict versioned schema. Stored `pending.method` values are re-filtered to the four stable families on every read. Public `acknowledged` requires a schema-valid identity-bound ack.

```
pwsh -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File src/lead-side/codex-app-server/Get-CodexAppServerLeadStatus.ps1 -SourcesPath YOUR_STATUS_SOURCES
```

Optional `-StateRoot` plus `-RunId` reads one run. Projected pending records contain only sanitized method and id.

## Explicit CLI fallback

Keep the current CLI Lead binding as an explicit choice. After a wake intent or app-server turn attempt, this adapter does not launch CLI. A schema, executable, profile, or version mismatch before any ambiguous write returns `fallback_required=cli` so the caller can bind the CLI launcher in a new dispatch. After bound/ack, compatibility drift stays on `recovery.json` for the same callback. Ambiguous delivery fails closed because automatic fallback can duplicate the turn.

## What this is not

The frozen v0.1 denominator is exactly eight routes, and no ninth is planned.

- not an adapter under `src/adapters/`
- not a second built-in Lead
- not a substitute for Telephone Line dispatch, receipt, or delivery authority
- not WebSocket, daemon, or experimental API support
